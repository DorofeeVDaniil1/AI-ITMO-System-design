# Мониторинг

Если не видно, что происходит на каждой проходной, система либо тихо копит FA, либо превращается в вечную очередь к охране. Ниже — что смотрю в эксплуатации. Бизнес-метрики подробно в [product.md](product.md); здесь — связь с техникой и ML.

## Технические метрики

- latency пайплайна: **p50 / p95 / p99** от кадра до команды (цель p95 ≤ 1 с)
- доступность камер и edge-узлов
- ошибки интеграции с турникетом (нет ack, повторные команды, таймауты)
- latency поиска по базе / ANN
- возраст кеша шаблонов и policy на edge (`cache_age`)
- доля запросов в degraded / offline

## ML-метрики

- false reject rate (оценка; точный FRR без delayed labels врать будет)
- доля `manual_review`
- доля отказов / review из-за quality
- liveness failures (серая зона и явный spoof отдельно)
- drift входа: распределение quality, размера лица, ракурса по камерам
- подтверждённые false accept (редкие, но каждый — инцидент)

## Бизнес (ссылка на product)

- время прохода / ожидание в пике
- доля автоматических проходов
- нагрузка на охрану (ручные разборы)

North Star и пороги guardrail — в product.md. Здесь важно: техметрики не «зелёные сами по себе», если очередь утром не сдвинулась или review% съел охрану.

## Что даёт CI (и чего не даёт)

GitHub Actions гоняет smoke на пяти событиях ТЗ и demo-скрипт. Это ловит регрессии **политики** fail-closed: e-1001 открывает, risky/offline не открывают, audit пишется.

CI **не** измеряет FAR/FRR, spoof на реальных атаках и p95 на железе проходной. Для этого нужны holdout по identity, delayed labels и пилот — см. [ml.md](ml.md). Зелёный pipeline ≠ «можно выкатывать авто-open на все ворота».

## Стартовые алерты

1. p95 latency > 1 с на проходной дольше N минут → смотреть камеру/GPU/очередь инференса, не крутить порог FAR.
2. Доля review > X% (например 15% в пике) → очередь у охраны, откат в assist/shadow.
3. Всплеск liveness fail на одной камере → сначала физика (блик, экран напротив), потом модель.
4. `cache_age` выше порога на edge → запрет auto-open (уже в policy), алерт эксплуатации на sync.
5. Любой **подтверждённый FA** → kill-switch авто-открытия на контуре, разбор по audit_id.
6. Турникет: рост ошибок ack → железо/сеть, не «модель тупит».

## Лампа vs модель

Если деградация на **одной** камере/проходной при нормальных остальных — чаще свет, грязь объектива, сдвиг камеры, новый экран напротив. Смотрю drift quality/ракурса и сырые кадры/статистику входа (не шаблоны всем подряд).

Если просело **сразу несколько** проходных после выкладки модели или массового re-enroll — подозреваю модель/пороги/индекс. Откат версии модели быстрее, чем «подкрутить T_allow в проде без holdout».

Срезы всегда: gate_id, camera_id, время суток, offline/online.

## Расследование через audit

У каждого решения есть `audit_id` / `event_id`. В логе: scores, reasons, employee_id (если был), turnstile_command, degraded_mode, позже — действие оператора. Сырого кадра по умолчанию нет; для review crop жил коротко.

Типичный разбор FA: audit → какой порог прошёл → была ли свежая policy → что сказал оператор / карта. Без audit_id «модель виновата» — гадание.

## Решается ли исходная задача

Раз в неделю (на пилоте — чаще) смотрю вместе:

- утреннее ожидание vs baseline по карте
- число ручных разборов «забыл карту» / отказ лица
- подтверждённые FA (должно быть 0)
- p95 и review%

Если latency в норме, а очередь не падает — узкое место не ML (поток, число турникетов, хвост review). Если FA=0, но review% убивает охрану — система безопасна и бесполезна, откатываем авто-режим.

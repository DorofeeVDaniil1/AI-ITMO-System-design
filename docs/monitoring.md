# Мониторинг

Если на проходных ничего не мерять, система либо тихо пустит чужого, либо превратится в вечную очередь к охране. Ниже — как я наблюдаю эксплуатацию: техника, ML, бизнес (бизнес подробно в [product.md](product.md)), алерты, как отличить камеру от модели, срезы по точкам, разбор через audit и проверка, что исходная боль вообще лечится.

В PoC есть простые счётчики `/metrics` и журнал `audit.jsonl`. В проде это же выносится в Prometheus/Grafana и центральный audit store.

---

## 1. Технические метрики

**Latency пайплайна.** Время от кадра (или события) до команды турникету. Смотрю не среднее, а процентили:

| Метрика | Зачем |
|---------|--------|
| p50 | «обычный» проход |
| p95 | цель из задания: ≤ 1 с |
| p99 | хвосты: очередь инференса, сеть, диск |

Если p95 растёт, а p50 почти нет — проблема в хвостах (очередь GPU, редкие таймауты), не в том что «модель всегда медленная».

**Доступность камер и edge-узлов.** Доля времени, когда камера отдаёт кадр и узел отвечает на `/health` (или аналог). Отдельно: рестарты, диск полный, температура GPU. Мёртвая камера выглядит для бизнеса как «лицо не работает», хотя модель ни при чём.

**Ошибки интеграции с турникетом.** Нет ack, таймаут команды, повторная отправка того же `event_id`, статус `duplicate` / отказ железа. Рост таких ошибок — чинить SDK/сеть/турникет, не порог match.

**Latency поиска по базе.** Время cosine / ANN на edge. На 12k brute-force обычно десятки мс; если внезапно сотни мс — индекс, нагрузка или слишком большой N без ANN.

Дополнительно (иначе слепой offline): возраст кеша шаблонов (`cache_age`), доля запросов в offline / degraded.

## 2. ML-метрики

| Метрика | Что это |
|---------|---------|
| **False reject rate (оценка)** | как часто своего не открыли автоматом. Без delayed labels (охрана / карта / жалобы) цифра врёт — см. [ml.md](ml.md) |
| **Доля ручных проверок** | `manual_review` / все события, особенно в пике 8:45–9:45 |
| **Доля отказов по качеству** | reason вроде `quality_below_threshold` — кадр плохой, не «модель лиц сломалась» |
| **Liveness failures** | отдельно серая зона (`liveness_uncertain` → review) и явный spoof (`liveness_spoof_suspected` → deny) |
| **Drift входа** | плывут ли распределения quality, размера лица, ракурса (yaw) по камерам |
| Подтверждённые false accept | редко, но каждый — инцидент и kill-switch, не «ещё одна кривая» |

Drift важный сигнал: если quality на камере A внезапно упал, а scores модели на других точках те же — сначала физика съёмки, не ретрейн.

## 3. Бизнес-метрики

Подробно и с порогами — в [product.md](product.md). Здесь только называю, что стыкую с техникой:

- время прохода / ожидание в утреннем пике;
- доля автоматических проходов (лицо открыло без охраны);
- нагрузка на охрану (ручные разборы в день).

Смысл стыка: зелёный p95 сам по себе ничего не значит, если очередь не упала или review% завалил пост.

## 4. Стартовые алерты

| Алерт | Что делаю |
|-------|-----------|
| p95 > 1 с дольше N минут на проходной | камера / GPU / очередь инференса; **не** ослабляю порог match |
| Доля `manual_review` в пике > ~15% | сужаю авто, больше карта / shadow; охрана в огне |
| Всплеск liveness-fail на **одной** камере | сначала свет, блик, экран напротив; потом PAD |
| `cache_age` выше порога на edge | auto-open и так запрещён правилами + алерт на sync отзыва |
| Подтверждённый false accept | kill-switch авто-открытия, разбор по `audit_id` |
| Рост ошибок ack турникета | железо / сеть / SDK |
| Камера или edge недоступны > порога | выезд / замена, не «крутить ML» |

N и точные проценты на пилоте фиксирую после первой недели shadow (чтобы не орать на шум).

## 5. Камера / свет vs деградация модели

**Похоже на камеру или освещение**, если:

- плохо только на одной `camera_id` / одном `gate_id`;
- соседние проходные в норме;
- одновременно упал quality / изменился ракурс / размер лица на входе;
- после уборки объектива, сдвига камеры или убирания монитора напротив стало лучше.

**Похоже на модель, пороги или индекс**, если:

- просело сразу несколько проходных;
- по времени совпало с выкладкой новой модели, сменой порогов или массовым re-enroll;
- drift входа (quality/ракурс) спокойный, а match/FRR разъехались;
- откат версии модели быстро возвращает картину.

Правило большого пальца: сначала срезы по камере и входная статистика кадра, потом версия модели. Порог FAR в проде без holdout не кручу «чтобы алерт пропал».

---

## 6. Деградация отдельно по проходным и камерам

Все ключевые ряды храню с разрезом минимум:

- `gate_id` (проходная);
- `camera_id`;
- час суток (пик / не пик);
- online / offline.

Смотрю дашборд «heatmap»: где выросли review%, quality-fail, liveness-fail, p95. Одна красная клетка = точечный выезд. Вся колонка красная после релиза = откат модели.

Без срезов средний FRR по кампусу прячет одну убитую камеру.

## 7. Расследование события через audit trail

У каждого решения в журнале есть связка `event_id` + `decision_id` / `audit_id`. В записи (как в PoC `audit.jsonl`):

- decision, turnstile_command, turnstile ack;
- reasons (почему так);
- match_score, margin, quality, liveness (в ответе API / quality-блоке);
- employee_id, если узнали;
- degraded_mode, network, cache_age;
- model_version / policy_version;
- позже — действие охраны (`operator_action`).

Сырой кадр по умолчанию не храню; для review crop жил коротко и отдельно.

**Типовой разбор «пустили чужого» или спорного open:**

1. Найти `audit_id` / `event_id`.  
2. Посмотреть reasons и scores — какой гейт прошёл.  
3. Проверить свежесть policy/кеша и версию модели.  
4. Было ли решение охраны или проход картой.  
5. Срез по этой камере за час — единичный сбой или паттерн.

Без audit trail фраза «модель виновата» — гадание.

## 8. Решается ли исходная задача

Раз в неделю на пилоте (на старте чаще) смотрю вместе технику и бизнес:

| Вопрос из боли | Что смотрю |
|----------------|------------|
| Утром меньше стоят? | ожидание 8:45–9:45 vs baseline по карте ([product.md](product.md)) |
| Охране легче с «забыл карту»? | число ручных разборов / день |
| Не пускаем чужих? | подтверждённые FA = 0 |
| Система вообще успевает? | p95 ≤ 1 с, review% в пике под контролем |

Выводы:

- latency в норме, очередь не падает → узкое место не ML (поток, число турникетов, хвост review);
- FA = 0, но review% убил охрану → безопасно и бесполезно, откат авто-режима;
- очередь упала, FA = 0, охрана не хуже baseline → исходная задача сдвигается в нужную сторону.

CI (pytest + demo) ловит только регрессии **политики** на фикстурах. Он не заменяет полевой мониторинг FAR/FRR и p95 на железе.

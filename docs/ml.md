# ML на проходной

Документ закрывает обязательный блок ТЗ по CV/ML. Модель даёт числа — scores. Правила решают: открыть, к охране или отказать. Пороги в PoC лежат в `poc/app/decision.py`.

---

## 1. CV/ML-задачи в системе и почему так

На горячем пути шесть задач подряд. Каждая отсекает свой класс ошибок до команды турникету.

**Детекция лица.** Нужно найти лицо в кадре (лучше одно крупное у турникета). Без детекции нечего сравнивать. Беру готовые детекторы вроде SCRFD / RetinaFace. В PoC детекта нет — в файле просто флаг «лицо нашлось».

**Оценка качества кадра.** Смотрю размытие, размер лица, свет, сильный поворот головы, маску. Плохой кадр — не открываю: иначе можно «узнать» мусор. Плохой свет и маска из задания бьют сюда — это отдельные срезы при проверке качества.

**Alignment.** Перед эмбеддингом выравниваю лицо по точкам глаз/носа. Иначе один человек при разном наклоне головы получит разный score. В InsightFace это обычно уже внутри.

**Liveness / anti-spoofing.** Защита от фото на телефоне, распечатки, видео с экрана. На проходной — пассивная проверка по одному кадру или короткому окну (чтобы уложиться примерно в секунду). Просить каждого «моргни» утром не хочу — очередь станет хуже. Серый liveness → охрана. Явная подделка → отказ. В PoC это mock-число из файла.

**Извлечение эмбеддинга.** Лицо превращаю в вектор чисел сетью класса ArcFace (часто через InsightFace) на компьютере у проходной. Свою сеть с нуля не учу: нет датасета, задание этого не просит.

**Сравнение с базой.** Считаю похожесть со всеми (или с кандидатами из индекса). Беру лучший score и отрыв от второго места (margin). Если отрыв маленький — к охране (кейс e-1004), не open.

### Как считаю похожесть

Есть вектор кадра `x` и шаблон сотрудника `e`.

```
cosine(x, e) = (x · e) / (|x| * |e|)
```

Если векторы заранее нормализованы до длины 1, это просто скалярное произведение: `x · e`.

Дальше сортирую всех сотрудников по убыванию score:

```
match_score = score_лучшего
margin      = score_лучшего − score_второго
```

Пример: лучший 0.78, второй 0.76 → margin = 0.02 — слишком мало, даже если 0.78 «в целом высокий».

## 2. Verification vs identification — что нужно на проходной

**Verification (1:1).** Человек как-то назвался (часто картой). Проверяем только его шаблон: `cosine(x, e_этого_id) >= порог`.

**Identification (1:N).** Имени нет. Ищем самого похожего во всей базе и смотрим и score, и margin.

На проходной без карты основной режим — **identification**. Verification оставляю, когда карта ещё есть, и как запасной путь: лицо не сработало → приложи карту. Если в MVP ходим только по лицу, 1:1 как основной путь не из чего собрать: некого «заявлять».

## 3. Поиск one-to-many на больших базах

Полный перебор: для каждого из N сотрудников считаем cosine с вектором длины d.

Порядок работы на 12 000 сотрудников и d = 512:

```
операций ≈ 12 000 × 512 ≈ 6 миллионов
```

На нормальном железе у проходной это обычно десятки миллисекунд — в секундный бюджет входит.

Если база вырастет до сотен тысяч (как в масштабе задания), полный перебор уже тяжёлый. Тогда на проходной ставят быстрый индекс (HNSW или Faiss): он не сравнивает со всеми подряд, а быстро находит похожих. Шаблоны по-прежнему хранятся в центре как «правда», на проходную копируются для скорости и offline.

В PoC сотрудников трое — индекс не делал, сравнение в лоб.

## 4. Пороги трёх исходов; false accept и false reject

Три ответа: `allow` (открыть), `manual_review` (к охране), `deny` (отказать).

Стартовые пороги из PoC (в проде — с holdout по людям):

| Имя в коде | Значение | Смысл |
|------------|----------|--------|
| Q_MIN | 0.55 | качество ниже → охрана |
| L_SPOOF | 0.35 | liveness так низкий → отказ (spoof) |
| L_ALLOW | 0.80 | ниже этого, но выше spoof → охрана |
| T_ALLOW | 0.75 | минимальный match для open |
| M_MIN | 0.12 | минимальный margin для open |
| CACHE_STALE_MINUTES | 120 | кеш старше → охрана, даже при красивом match |

### Когда открываю

Открываю **только если всё сразу** выполнено:

1. лицо найдено  
2. quality >= 0.55  
3. liveness >= 0.80  
4. match_score >= 0.75  
5. margin >= 0.12  
6. человеку можно на эту проходную  
7. возраст кеша шаблонов <= 120 минут  

Если liveness <= 0.35 или политика жёстко запрещает → **deny**.  
Всё остальное сомнительное → **manual_review**, турникет не открывается.

### Пример на событиях из задания

| Событие | quality | liveness | match | margin | Что получается |
|---------|---------|----------|-------|--------|----------------|
| e-1001 | 0.883 | 0.947 | 0.812 | 0.168 | open: всё выше порогов |
| e-1002 | 0.318 | 0.902 | — | — | охрана: quality 0.318 < 0.55 |
| e-1003 | 0.804 | 0.176 | — | — | отказ: liveness 0.176 <= 0.35 |
| e-1004 | 0.706 | 0.879 | 0.783 | 0.041 | охрана: margin 0.041 < 0.12 |
| e-1005 | 0.861 | 0.934 | 0.837 | 0.191 | охрана: нет сети и кеш 240 мин > 120 |

Счёт e-1001: 0.812 >= 0.75 и 0.168 >= 0.12 → можно открывать.  
Счёт e-1004: match вроде ок (0.783 >= 0.75), но margin слишком маленький → не открываю.

### False accept и false reject

- **False accept (FA)** — пустили чужого.  
- **False reject (FR)** — не пустили своего.

Считаю доли так:

```
FAR = (сколько раз открыли чужому) / (сколько было чужих попыток)
FRR = (сколько раз своего не открыли автоматом) / (сколько было своих)
```

На проходной «открыли» значит прошли все проверки выше, а не только match >= порога.

FA для меня важнее FR: чужой внутри — инцидент; свой идёт к охране или достаёт карту. Поэтому порог на open ставлю жёстко и не ослабляю его «чтобы утром быстрее шли».

Ориентир пилота: FAR порядка 0.0001 и ниже. FRR и долю ручного разбора смотрю отдельно — чтобы не убить охрану.

Как двигается компромисс, если крутить только порог match (порядок на holdout):

| Порог match | FAR (порядок) | FRR (порядок) | Что это значит |
|-------------|---------------|---------------|----------------|
| 0.70 | ~0.0003 | ~2% | очередь легче, чужих пускаем чаще |
| 0.75 | ~0.0001 | ~4% | рабочая точка пилота |
| 0.80 | ~0.00002 | ~8% | безопаснее, больше людей к охране/карте |

**EER** — порог, где FAR ≈ FRR. В проде в этой точке не живу: ухожу в сторону меньшего FAR.  
**ROC** — кривая FAR против доли правильно принятых своих при разных порогах.  
**PR** — precision/recall отдельно для «кто это» и для «это не подделка».

## 5. Что решает модель, а что правила

| Считает модель / эвристика | Решают правила |
|----------------------------|----------------|
| есть ли лицо, quality, liveness, вектор, scores по базе | хватает ли порогов; можно ли человеку сюда; не протух ли кеш; не открывали ли уже это событие; что делать, если модели нет |

Модель турникет не открывает. Она даёт числа. Open / hold / deny — после правил.

## 6. Готовые предобученные модели vs собственные данные

**Готовые модели уместны** на горячем пути: детекция, ArcFace-эмбеддер, passive anti-spoof.

**Свои данные нужны** не чтобы учить FR с нуля, а чтобы:

- подогнать пороги quality / liveness / match / margin под наши камеры;
- проверить anti-spoof на наших телефонах и ракурсах;
- померить ошибки по свету, маске, конкретным камерам.

Без полевых данных пороги с чужих бенчмарков на кампусе могут врать.

## 7. Какие baseline запустить первыми и какие метрики смотреть

**Первый прогон:** InsightFace (найти лицо + выровнять + эмбеддинг) + простая оценка качества + отдельный passive PAD. На 12 тысяч — обычный перебор cosine. Быстрый индекс — когда база вырастет.

**Технические метрики выбора (как просит ТЗ):**

| Метрика | Зачем смотрю |
|---------|----------------|
| FAR / FRR | основная рабочая точка порогов |
| EER | ориентир на кривой; в проде не цель |
| ROC / PR | отдельно «кто это» и «не подделка» |
| latency p95 | успеваем ли примерно за 1 секунду |

Грубый бюджет времени до команды турникету:

| Стадия | Ориентир |
|--------|----------|
| детекция + качество | 80–100 мс |
| liveness | 100–150 мс |
| эмбеддинг | 250–400 мс |
| поиск + margin | 30–80 мс |
| правила + команда | 10–20 мс |
| запас | остаток до 1000 мс |

Если p95 больше секунды — чиню железо и эмбеддинг, а не ослабляю порог match.

## 8. Validation set, leakage, подгруппы, delayed labels

**Как собираю validation.** Делю данные **по людям**, не по кадрам. В выборке разные камеры, дни, свет, маска/очки, online/offline. Фото при регистрации и кадр на проходе — не из одного ролика.

**Как избегаю leakage.** Люди, на которых кручу пороги, не пересекаются с теми, кто уже в рабочей галерее для «красивого» отчёта. Иначе цифры завышены.

**Качество по подгруппам.** Считаю FAR / FRR / долю охраны не только средним по кампусу, а отдельно по проходным, камерам, времени суток, маске, свету. Иначе одна плохая камера прячется в среднем.

**Delayed labels (догоняющая правда).** В момент прохода часто неизвестно, кто это был. Потом дописываю метки из:

- решения охраны на ручной проверке;
- жалоб сотрудников («меня не пустило»);
- факта, что после отказа лица человек всё же прошёл по карте.

Так уточняю FAR/FRR на пилоте. Без этого «зелёный» только demo на заранее подставленных файлах.

## 9. Нужен ли LLM (отдельный абзац)

В контуре allow / deny / open LLM **не использую**. Здесь нужны стабильные числа вроде quality = 0.88, match = 0.81, margin = 0.16 и понятные пороги — по ним считается FAR/FRR и пишется журнал. У языковой модели нет такого калиброванного порога на лицах, ответ плохо разбирать («почему открыли»), плюс лишняя задержка. Позже его можно представить сбоку: текст для охраны или поиск по журналу. Но не тот модуль, который решает, открыть турникет или нет.

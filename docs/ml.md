# ML на проходной

Горячий путь — цепочка CV-задач + правила сверху. Модель даёт scores. Открывать турникет или нет — policy, не «argmax по softmax».

## Задачи на кадре

**Детекция.** Найти лицо (лучше одно доминирующее у турникета). Baseline: SCRFD / RetinaFace. В PoC — fixture или грубый OpenCV, это не про качество детекции.

**Качество.** Blur, размер лица в кадре, экспозиция, сильный yaw/pitch, маска/очки как сигнал риска. Плохой кадр → не allow. Иначе ловим ложные match на мусоре и раздуваем FRR «не тем способом».

**Alignment.** По landmarks выровнять crop перед эмбеддингом. Без этого один и тот же человек прыгает по score из-за поворота. Pretrained пайплайн (InsightFace и аналоги) обычно тянет это вместе с embedder.

**Liveness / anti-spoof.** Нужны как минимум атаки: фото на телефоне, распечатка, replay с экрана. На горячем пути — **passive PAD** (один кадр / короткое окно), чтобы уложиться в 1 с. Active challenge (моргни, поверни) — не happy path: тормозит очередь. Серый liveness → manual_review. Явный spoof → deny + алерт. В PoC score из fixture — честный mock.

**Эмбеддинг.** ArcFace-класс (InsightFace и т.п.) на edge. Свои веса с нуля не учу в этом кейсе — нет нормального датасета и ТЗ это прямо не просит. Свои данные нужны для **калибровки порогов и PAD под наши камеры**, не для «ещё одной FR-сети».

**Сравнение с базой.** Cosine / similarity top-2: best score и margin до второго. Margin маленький → два похожих кандидата → review (e-1004), не allow.

Условия съёмки из ТЗ (контровый свет, маска, шапка, yaw) бьют по quality и FRR. Это не «добавим аугментаций в презентацию», а отдельные срезы в validation.

## 1:1 vs 1:N

**Verification (1:1):** «этот кадр = этот claimed id» (часто лицо+карта).

**Identification (1:N):** «кто это из базы».

На проходной без карты — identification. Verification оставляю на shadow/assist (карта есть) и как fallback. На MVP без карты 1:1 бессмысленен: некого claim'ить.

## Поиск one-to-many

12k сотрудников — полный перебор нормализованных векторов на GPU/CPU edge укладывается в десятки миллисекунд. «Сотни тысяч» из ТЗ — уже ANN: HNSW или Faiss IVF-PQ на edge, реплика из центра. PoC: крошечная gallery + brute-force cosine. В архитектуре ANN заложен, в коде кейса его нет — незачем раздувать PoC.

## Три исхода и пороги

Исходы: `allow` | `manual_review` | `deny`.

Allow только если **все** гейты зелёные:

- лицо найдено, quality ≥ Q_min
- liveness ≥ L_allow (и не в spoof-зоне)
- match ≥ T_allow
- margin ≥ M_min
- policy пропускает сотрудника на эту проходную
- кеш шаблонов не протухший (иначе даже хороший match → review)

Иначе:

- явный spoof / жёсткий policy deny → `deny`
- серая зона (качество, liveness, margin, stale cache, offline риск) → `manual_review`

**FAR дороже FRR.** False accept — посторонний в контуре. False reject — очередь и охрана. Assumption цены подтверждённого FA: **250 000 ₽** (расследование + аудит доступа + простой). Поэтому FAR — kill-switch пилота (стоп авто-открытия), а не «подкрутим порог, чтобы утром быстрее шли». Цели порядка: пилот FAR ≤ 1e-4, прод ≤ 1e-5; FRR и % review смотрим отдельно как guardrail бизнеса.

Пороги калибрую на holdout **по identity**, не подгоняю на тех же людях, что в gallery.

## Что модель, что правила

| Модель | Правила / policy |
|--------|------------------|
| detect, quality net, PAD, embedder, similarity | пороги Q/L/T/M, access policy, freshness кеша, идемпотентность, fail-closed при отсутствии модели |

LLM в матчинг не лезет (см. ниже).

## Baseline и метрики выбора

Первым прогоном: готовый detect+embed (InsightFace-стек) + простой quality-эвристики + отдельный PAD. Сравниваю не «accuracy одной цифрой», а:

- FAR / FRR при фиксированных рабочих точках
- EER (ориентир, в проде рабочая точка смещена в сторону низкого FAR)
- ROC / PR по spoof и по identification
- latency p95 пайплайна на edge-железе

Выбор порога — trade-off на кривой, с якорём «FAR не выше X».

## Validation без самообмана

- **Сплит по личностям**, не по кадрам. Иначе один человек в train и test — leakage, пороги врут.
- Разные камеры, дни, освещение, маски/очки — отдельные срезы. Средний FRR по кампусу может прятать проходную с контровым светом.
- Enrollment и probe не из одного клипа.
- **Delayed labels:** решение охраны, жалоба сотрудника, проход по карте после отказа лица — догоняющие метки для разбора FA/FRR. Без них пилот «зелёный» только на синхронных фикстурах.

## LLM

В контуре allow / deny / open — **нет**.

Нет калибруемого FAR, нет стабильного аудита («почему открыли»), латентность и галлюцинации на биометрии — плохая идея. Допустимо позже вне горячего пути: черновик текста для охраны или поиск по audit. Не matcher.
